# Proposal

## Why

本專案現有 `npm run check:lang` 僅以手寫簡體字集與中國用語表進行硬閘門掃描，回報「0 違規」只能證明未命中精簡對照表，無法證明文件已完整符合臺灣繁體用語；另一方面，OpenCC `s2twp` 雖能補足詞典覆蓋率，卻是轉換器而非語言規範判定器，會誤改本專案既有的正確資料契約與臺灣慣用語。實測在 Node 24 的結果更明確：`s2tw`（字級）對繁體「項目」「數據」「課程代碼」「權限」與「報告項目」**完全不變**，只對真正的簡體字（`\u9879\u76ee`、`\u6570\u636e`、`\u6743\u9650`）產生差異；`s2twp`（字級＋片語）卻把繁體「項目→專案」「課程代碼→課程程式碼」「權限→許可權」，連簡體 `\u6743\u9650` 也誤改為「許可權」。這證明兩件事：① 候選定位應由 `s2tw` 差異決定，才不會把正體詞誤當成問題；② `s2twp` 只能對已定位候選提供慣用語建議供人工挑選，不能做為機械取代或 CI 判定依據（繁體「鼠標」因 `s2tw` 無差異，其「滑鼠」建議不會出現）。第五輪壓力測試另發現，既有硬閘門的 `\u652f\u6301`、`\u914d\u7f6e`、`\u53bb\u91cd`、`\u54c8\u5e0c` 全由正體字組成，`s2tw` 對其無差異，在新設計下永不成為候選；因此必須明文界定候選工具範圍，並讓 CI 在「有違規但零候選」時發出警告，避免形成「硬閘門紅燈、報告零候選」的假保險。來源專案 KSVS-Course-Information-Collector 已於 commit `81935296ea8cb2c4661438b3e92835e4cf2d27c8` 建立只回報、不強制改寫的候選定位工具；本提案將該能力移植並依上述洞察調整：保留原有硬閘門做為向後相容錨點，新增 `s2tw` 定位／多來源建議／人工選詞／全數核准後才寫入的輔助流程，同時不破壞既有工作表表頭、Action 名稱、角色權限字面值與測試契約。

## What Changes

- 新增官方 `opencc`（精確鎖定 `1.4.2`，Apache-2.0）與 `@babel/parser`（精確鎖定 `7.29.15`）為 **devDependency**，僅供 Node 工具鏈使用，不進入 GAS 後端或前端打包產物；採延遲載入與 `OPENCC_UNAVAILABLE` 結構化降級，原生套件不可用時既有硬閘門仍照常執行。`s2tw.json` 用於定位、`s2twp.json` 用於建議，兩者皆載入中繼資料。已於 Node 24 實測黃金案例與正體不變案例，並以 `npm run language:smoke`（`node scripts/openccS2twp.js --smoke`）做為 CI 非阻斷可用性檢查。
- 新增 `quality-core/` 純函式核心（穩定 ID、候選比對與分層、受保護詞彙 trie 與 PUA 集合不變式、文字差異比對、契約漂移比對），並納入本專案既有的 c8 覆蓋率與 CRAP／MI 品質度量範圍；確認 `.claspignore` 不會將其上傳至 Apps Script。
- 新增 `scripts/openccS2twp.js` 薄封裝（`createConverter`／`convertText`／`getMetadata`，同時提供 `s2tw` 與 `s2twp` 轉換器）、`scripts/openccS2twpProtectedTerms.js` 受保護術語外殼、`scripts/openccS2twpApprovals.js` 內容定址核准清冊，以及 `scripts/generateOpenccS2twpContractLiterals.js` 契約字面值清冊產生器。
- 擴充 `scripts/languageCheck.js` 為四模式：預設檢查、`--report` 結構化報告、`--dry-run` 乾跑、`--fix` 有限寫入，並新增 `--approve`／`--revoke` 核准操作。**候選存在與位置由 `s2tw` 差異決定；`s2twp` 差異不得單獨建立候選，且其建議僅附加在已定位候選上；由正體字組成的既有中國用語違規不進候選工具，仍由硬閘門回報並人工修正**。`original` 粒度明確：命中硬違規詞時取該詞完整字面，否則取 `s2tw` 差異的最小替換單元，並據此計算 ID 與 `occurrenceIndex` 鍵；此規則僅適用於同時命中 `s2tw` 差異者，且先決定 `original` 再進行最長優先重疊合併。每筆候選提供 `suggestionOptions` 陣列（`{ source, text }`，來源值域 `S2TW`／`S2TWP`／`MAINLAND_TERMS`），預設建議為最保守的 `S2TW` 字級結果；人工判斷上下文挑選後，須以 `--approve` 明確綁定所選建議，**所有寫入一律須核准**，`--fix` 只寫入核准紀錄指定的建議，不再有「高精度建議可自動寫入」的路徑。`rule` 值域仍為 `HARD`／`S2TWP`，僅供排序與標示，不構成寫入授權。`language:check` 嚴格等同 `--dry-run`，不取代 `check:lang`。
- 核准 ID 採內容定址，以 `\0` 分隔 `file`、`original`、`contextHash`、`occurrenceIndex` 四個欄位後取 SHA-256 前 16 碼，**不含行號、欄位偏移或 `suggestion`**；候選身份即「簡體字出現的位置」，替換詞彙由核准紀錄另行綁定，並以「所選建議須存在於目前 `suggestionOptions`」驗證防止建議漂移。可容忍整行位置移動，但**同行重新格式化、前方插入相同字面值或上下文改變時即失效並須重新核准**，此限制將明確文件化。授權決策表最前加入 `⓪` 守門：任一識別欄位含 `\0` 時立即回 `INVALID_RECORD`，杜絕含分隔符且 ID 自洽的紀錄取得授權。
- 核准清冊與 JSONL 採序列化層：`JSON.stringify` 後對所有非 ASCII 字元逐 UTF-16 程式碼單元做 `\uXXXX` JSON 標準跳脫（檔案中為單一 `\` 加 `u` 加四位十六進位，代理對兩碼元各四位，禁用 `codePointAt`），使檔案為純 ASCII；`JSON.parse` 為唯一解碼點且解析後不得字串替換。`saveRegistry()` 為唯一寫入點，每次皆驗證純 ASCII 與識別碼相符；清冊版本僅接受數值 `1`，不匹配時 fail-closed 並輸出 `APPROVALS_VERSION_UNSUPPORTED`。
- `--fix` 載入報告時保留報告 `id` 為 `reportedId` 做為否決與診斷證據並另行計算目前 `id`；報告的 `approvalState`／`suggestion`／`suggestionSource` 一律不信任，必須重新計算。`reportedId` 不得做為正向授權來源，但 MUST 被查詢做為衝突與失效診斷。由共用的 `authorizeCandidate()` 判別 `AUTHORIZED`／`UNAPPROVED`／`INVALID_RECORD`／`ORIGINAL_MISMATCH`；`isStableIdValid(id, registryEntryFields)` 明確定義為「16 碼十六進位格式、核准紀錄四欄位不含 `\0`，且以目前演算法重新計算**該紀錄自身四欄位**相符」，不得以目前候選欄位重算，否則格式化情境會先回 `INVALID_RECORD` 使 `ORIGINAL_MISMATCH` 再次不可達；工具版本升級使 ID 演算法改變時舊紀錄回 `INVALID_RECORD`（四欄位與候選相同時診斷 `ID_ALGORITHM_CHANGED`、欄位遭竄改時診斷 `APPROVAL_TAMPERED`，診斷延遲至 `authorizeCandidate()` 判定且兩者可區隔），而非不可達的升級分支；建議選項漂移、`file`／`original`／`contextHash`／`occurrenceIndex` 任一改變，或目前 ID 與 `reportedId` 指向不同建議時回 `ORIGINAL_MISMATCH`。兩類失效皆禁止寫入並要求重新核准，杜絕失效核准因格式化、竄改或工具升級而復活。清冊 `approvals` 須為 plain object，查表僅用 `Map` 或 `Object.hasOwn()`，含 `__proto__`／`constructor`／`prototype` 鍵即 fail-closed 拒絕載入；工具為本機單一執行，明文禁止並行核准與撤銷，避免舊快照覆蓋使已撤銷核准復活。
- 新增 `artifacts/language-report.jsonl` 與 `language-report.md` 結構化報告，並將 `artifacts/` 納入 `.gitignore`、`.prettierignore` 與硬閘門排除清冊（此為本變更新增目錄）；所有工具產生文件在呈現 `original`／`suggestion`／`suggestionOptions` 時，將所有非 ASCII 字元一律做 `\uXXXX` 跳脫（與序列化層一致，不逐詞比對禁詞表），確保任意根目錄內輸出路徑都不使硬閘門由綠轉紅。報告 meta 含 `generatedAt`、`degraded`、`degradedReason`、`literalDrift`、`violationCount`、`exemptLines`、`candidateCount`、`protectedCount`、`unprotectedCount`、`exemptCandidateCount`（屬 `unprotectedCount` 子集，且 `protected` 優先於 `exempt`，同一候選不得同時標記兩者）、`tierCounts`、`protectedTermsStatus` 與 `outOfScopeFiles` 等欄位；寫入失敗在 stderr 輸出 `REPORT_WRITE_FAILED`、在 stdout 輸出狀態與位元組數，結束碼仍為 0。
- 新增以 AST 靜態產生的測試契約字面值清冊與 `--check` 漂移警告，並定義「大量移除」門檻為 `max(10, ceil(清冊筆數 × 0.05))`；受保護清冊必須涵蓋本專案的工作表名稱常數、角色顯示名稱、`logLabel`／`logDetailKey` 等 Action 中文中繼資料與法定單位。繁體「項目」及其 s2twp 誤改結果「專案」雙向納入受保護清冊；`s2tw` 定位已使繁體「項目」不產生候選，此保護用於防止正體原文位置被改寫。**保護是候選原文的屬性**：受保護候選與豁免候選一律不寫入；但候選原文為真正簡體違規（如 `\u9879\u76ee`）時，人工核准的建議即使字面為「專案」仍得寫入，此為修正簡體違規而非誤改正體詞。受保護來源載入失敗時 MUST 輸出 `PROTECTED_TERMS_UNAVAILABLE` 並記錄於報告 meta，不得靜默降為空清單。
- CI 品質閘門在既有強制檢查之外，新增**非阻斷**的可用性 smoke、報告產生、漂移檢查、報告構件檢查與構件上傳；構件檢查 MUST 解析報告首行 meta 的 `degraded`、`candidateCount`、`exemptCandidateCount`、`violationCount` 與 `generatedAt`，避免「檔案存在但全員降級或沿用舊報告」的假保險；`violationCount` 定義為與硬閘門同範圍（含 `openspec/`、`docs/參考資料/`，僅排除 `artifacts/`）的違規總數，由報告模式**直接呼叫 `checkProject()` 純函式加總**取得，不受報告排除清冊影響，且不得呼叫 `main()` 或輸出硬閘門違規原文。既有 Language check 步驟宣告 `id: language-hard-gate`，硬閘門成敗布林 `hardGateFailed` 由 `steps.language-hard-gate.outcome != 'success'` 取得，再以 `hardGateFailed !== (violationCount > 0)` 交叉比對，不得讀不到就當零，亦不得對布林值使用 `!== 0`（嚴格不等式因型別不同而恆真）；構件檢查亦驗證報告非空。當 `violationCount > 0`、`candidateCount = 0` 且 `degraded` 為 false 時輸出單一警告，文案以 spec「有違規但零候選須警告」場景之完整字串為單一來源（降級造成零候選時改由降級警告處理）；「全數受保護／全數豁免」僅在 `candidateCount > 0` 時由獨立警告處理。警告維持非阻斷，但工作流程摘要須輸出固定錨點 `LANGUAGE_SIGNOFF_REQUIRED` 與「語言警告未處理，合併前須人工簽核」並標記 PR 為 `language-signoff-required`，標籤新增失敗時摘要額外警示；核閱文件 SIGNOFF 欄位標註「語言警告已處理，合併前人工簽核」；`AGENTS.md` 禁合流程補充「錨點或標籤存在且 SIGNOFF 空白時不得 squash merge，且須主動檢查工作流程摘要，不因標籤缺失放行」。`generatedAt` 有效窗口為基準時刻前 15 分鐘至後 5 分鐘，避免舊構件被誤判。**CI 步驟僅判斷簡體字出現與候選證據，不得執行 `--fix`／`--approve`／`--revoke` 或寫入任何原始檔。**
- 新增 `README.md`、`AGENTS.md` 的操作說明與來源註記文件（`docs/參考資料/opencc/SOURCES.md`，含 Node 24 實測與 s2tw／s2twp 差異對照），並產出全專案掃描核閱結論文件；調整 `.claspignore` 使新增 Markdown／PDF／CSV 不上傳，同時確認 7 個離線手冊 HTML 仍可上傳。「零違規僅為向後相容錨點」的說明寫入文件，不改變 `check:lang` 輸出。

## Capabilities

### New Capabilities

- `zh-tw-language-conformance`: 定義臺灣繁體語言合規工具的可觀察行為，包含官方 `s2tw` 定位與 `s2twp` 建議封裝與降級、`s2tw` 差異候選定位、多來源建議與人工選詞、純函式分析核心、`suggestionOptions` 與結構化報告、內容定址核准與全數核准後寫入、受保護術語與契約字面值防護，以及 CI 非阻斷只報不寫的報告契約。

### Modified Capabilities

- `system-settings-and-docs`：既有 main spec 要求 `.claspignore` 加入 `!docs/` 與 `!docs/**`，會將新增的 `docs/參考資料/**/*.md`、`docs/opencc-s2twp-review.md`，以及既有的 `docs/quality-baseline-2026-11-20.md` 一併上傳 GAS。本次將放行規則縮窄為 `!docs/` 與 `!docs/**/*.html`，保留 7 個 `WEB_APP_DOC_ROUTES` 白名單 HTML 的上傳，同時排除上述 Markdown 與其他非 HTML 檔案；以 delta spec 明確改寫該 requirement，避免封裝後 main spec 與實作漂移。
- 既有 `developer-tooling-and-quality` 的硬閘門判定來源、輸出格式與結束碼維持不變，不列入修改。

- **修改檔案**：`package.json`、`scripts/qualityConfig.js`（`SCOPE.include`／`SCOPE.sourcePatterns`）與 `tests/qualityConfig.test.js`（僅更新精確範圍陣列與第 5 行過期註解；`measuredAt`、`miMin`、`crapMax` 與 2026-11-18 過期快照等歷史地板／歷史比較斷言完整保留）、`scripts/checkComplexity.js`、`scripts/checkChangedCoverage.js`、`scripts/quality-baseline.json`（更新 `scope.include`／`scope.files`／`scope.methods`，並保留 `measuredAt`、`miMin`、`crapMax`、`ratchet` 與歷史快照比較）、`scripts/languageCheck.js`、`.github/workflows/quality-gates.yml`、`.claspignore`、`.gitignore`、`.prettierignore`、`tests/languageCheckAnon4.test.js`、`tests/qualityGatesWorkflow.test.js`、`tests/qualityDocumentation.test.js`、`README.md`、`AGENTS.md`。本專案 **沒有** `scripts/coverage-config.js`，品質設定單一來源為 `scripts/qualityConfig.js`，不可照抄來源檔名。
- **相依與環境**：新增 `opencc@1.4.2` 與 `@babel/parser@7.29.15` 兩個精確版號 devDependency；本專案已使用 Node 24（`engines.node >=24.0.0`、CI `node-version: "24"`），移植時以 CI 非阻斷 smoke 與來源註記記錄實測結果，不採來源專案的 Node 20 鎖版。
- **相容性**：不改變後端 GAS 執行環境、前端打包流程、`check:lang` 的違規判定來源／輸出格式／豁免標記／結束碼或既有 API 與工作表資料契約。既有硬閘門刻意將 `openspec/` 與 `docs/參考資料/` 納入掃描，此政策與 `tests/languageCheckAnon4.test.js` 契約 MUST 維持不變；硬閘門唯一新增排除項為本變更才產生的 `artifacts/`（採 basename 比對，可接受同名子目錄一併排除並以測試鎖定），報告／乾跑／修正／核准模式另用相對路徑前綴清冊額外排除 `openspec/`、`docs/參考資料/`、`dist/`、`build/` 等。`.claspignore` 現行 `**` 規則已排除子目錄模組，仍須驗證 `quality-core/` 不上傳，並避免新增 Markdown 文件因 `!docs/**` 被上傳。
- **品質度量連動**：純函式核心納管後必須補足測試，使 CRAP ≤ 25、MI ≥ 50、全域覆蓋率與基準線不回退、變更行與分支覆蓋率 ≥ 80%；若需更新基準，SHALL 依既有 `coverage-and-complexity-gates` 規格重新量測並文件化，且不得下修既有歷史地板。
- **主要風險**：`s2twp` 過度轉換已由 `s2tw` 定位與人工選詞從根源降低，但核閱者仍可能選錯建議，須以受保護清冊、繁體「項目」雙向保護、核准清冊綁定所選建議與逐筆核可收斂；核准清冊可為空白，工具上線不代表自動改寫全專案。另一風險為純函式核心納入品質度量後拉低 ratchet 指標，需以契約測試與重新量測因應。第三風險是由正體字組成的違規形成「硬閘門紅燈、報告零候選」假保險，須以 CI `violationCount` 警告與核閱文件逐條人工修正證據收斂；第四風險為建議漂移、格式化、並行覆蓋或工具升級使失效核准復活，須以 `ORIGINAL_MISMATCH`（內容變動）、`INVALID_RECORD`（含可區隔診斷 `ID_ALGORITHM_CHANGED` 與 `APPROVAL_TAMPERED`）、四欄位比對、原型鍵 fail-closed 與禁止並行操作防堵；第五風險為竄改報告欄位繞過核准，須以「報告非授權來源」與重新計算因應，並文件化「直接改寫清冊等同核准，信任邊界為 PR 核閱」；第六風險為非阻斷警告被忽略，須以工作流程摘要固定錨點、PR 標籤（失敗時額外警示）、核閱文件 SIGNOFF 與 `AGENTS.md` 禁合流程強制可見；第七風險為零候選警告列舉與計數定義自我矛盾，須以單一原因警告、`degraded === false` 條件與 `exemptCandidateCount` 獨立警告收斂。
