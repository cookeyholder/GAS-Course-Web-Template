## Purpose

定義操作日誌的完整行為，讓系統能回答誰在何時執行了什麼動作、變動了哪些內容，並在容量與隱私受到控制的前提下提供可查閱的稽核軌跡。

## ADDED Requirements

### Requirement: 操作日誌工作表於初始化時建立且保持冪等

資料庫初始化流程 MUST 建立獨立的操作日誌工作表，欄位至少包含時間戳記、請求識別碼、事件類別、動作名稱、結果、操作者 email、操作者姓名、角色、摘要、詳情 JSON、耗時（毫秒）與錯誤代碼共 12 欄；工作表 MUST 具備凍結標題列，詳情欄位 MUST 預先套用純文字格式。時間戳記 MUST 統一採用 Asia/Taipei 時區。既有試算表執行初始化時 MUST 自動建立該表且不影響既有工作表；重複初始化 MUST 保持冪等，不得建立重複工作表或覆寫既有日誌。工作表名稱 MUST 由前後端共用的執行環境模組單一提供。

#### Scenario: 全新試算表建立日誌工作表

- **WHEN** 對尚未建立操作日誌工作表的試算表執行初始化
- **THEN** 建立具備完整欄位與凍結標題列的操作日誌工作表，既有工作表不受影響

#### Scenario: 既有試算表補建日誌工作表

- **WHEN** 對已有其他工作表但缺少操作日誌工作表的試算表執行初始化
- **THEN** 僅新增操作日誌工作表，既有工作表與其資料保持不變

#### Scenario: 重複初始化保持冪等

- **WHEN** 已存在操作日誌工作表時再次執行初始化
- **THEN** 不建立重複工作表，既有日誌資料不被覆寫或清空

### Requirement: 所有動作皆產生完整請求日誌

Web API 進入點 MUST 為每一次非例外請求建立唯一的請求識別碼與開始時間，並在請求結束時寫入恰好一列日誌，覆蓋寫入動作、查詢動作、登入、登出與各類失敗。日誌 MUST 記錄事件類別、動作名稱、執行結果、耗時與操作者身份；操作者身份 MUST 在授權成功後由 session 寫回請求層級的 log context，角色顯示名稱 MUST 由角色代碼取得而非讀取 session 上不存在的欄位；公開登入動作成功時 MUST 從回傳結果補寫已驗證身份。`ping`、`getPublicConfig` 與 `getActivityLog` MUST NOT 寫入日誌。

#### Scenario: 寫入動作產生日誌

- **WHEN** 通過授權的寫入動作執行完成
- **THEN** 寫入一列含完整操作者身份與執行結果的日誌

#### Scenario: 查詢動作產生日誌

- **WHEN** 通過授權的查詢動作執行完成
- **THEN** 寫入一列日誌，其中包含篩選條件、分頁資訊與回傳筆數，且不含回傳內容本身

#### Scenario: 心跳與日誌查閱不寫入日誌

- **WHEN** 呼叫 `ping`、`getPublicConfig` 或 `getActivityLog`
- **THEN** 不寫入任何日誌列，避免心跳與查閱行為自我增生

#### Scenario: 登入成功記錄已驗證身份

- **WHEN** `login` 或 `loginWithActiveUser` 成功建立 session
- **THEN** 日誌的操作者 email、姓名與角色取自該次已驗證的登入結果，而非標記為未驗證

### Requirement: 失敗嘗試亦須留下稽核記錄

請求在解析、路由、授權或 CSRF 驗證階段失敗時 MUST 仍寫入日誌，記錄失敗類別與錯誤代碼。此攔截 MUST 位於 Web API 進入點的最外層，使 JSON 解析失敗與缺少 action 等提前回傳情境亦被記錄。無法取得已驗證身份時，操作者欄位 MUST 明確標記為未驗證或留空，不得將未驗證的 email 當作已確認身份；失敗嘗試的字串欄位 MUST 先截斷至 500 字元再寫入。

#### Scenario: JSON 解析失敗仍寫入日誌

- **WHEN** 請求 payload 為無效 JSON 而無法解析
- **THEN** 寫入一列結果為失敗、錯誤代碼標示解析失敗的日誌，且不寫入未驗證的身份資訊

#### Scenario: 授權失敗仍寫入日誌

- **WHEN** 請求因未授權或角色不符被拒絕
- **THEN** 寫入一列含失敗類別與錯誤代碼的日誌

#### Scenario: 超長輸入被截斷

- **WHEN** 失敗請求帶入超過 500 字元的字串
- **THEN** 日誌中該欄位被截斷至 500 字元，不寫入原始超長內容

#### Scenario: 缺少 action 仍寫入日誌

- **WHEN** 請求未帶 action 參數而提前回傳
- **THEN** 寫入一列錯誤代碼標示缺少動作的日誌

### Requirement: 日誌詳情採資料最小化與結構化變動明細

日誌詳情 MUST 以結構化格式記錄彙總指標與變動明細，且 MUST NOT 包含 CSRF token、session token、原始上傳資料列或查詢回傳內容。需要記錄變動內容的動作 MUST 在寫入前擷取快照並於寫入後計算差異，產生含欄位名稱、變更前值與變更後值的明細；每筆詳情紀錄 MUST 標示版本號以便日後格式演進。

#### Scenario: 匯入動作記錄筆數

- **WHEN** 課程代碼匯入完成
- **THEN** 日誌詳情包含上傳筆數與展開筆數等彙總指標，且不含原始資料列

#### Scenario: 匯入驗證失敗或冪等命中

- **WHEN** 課程代碼匯入因驗證失敗而無統計資料，或命中先前快取結果
- **THEN** 日誌詳情明確標記統計不適用或標示為冪等命中，不寫入未定義的筆數

#### Scenario: 系統設定記錄變動明細

- **WHEN** 系統設定被修改並存檔
- **THEN** 日誌詳情包含每個變動欄位的名稱、變更前值與變更後值

#### Scenario: 敏感資料不外顯

- **WHEN** 任一請求的 payload 或結果含有 token 或原始上傳列
- **THEN** 寫入日誌的詳情不含上述敏感內容

### Requirement: 日誌容量受控且清理於離峰執行

操作日誌 MUST 設定 20,000 列的清理閾值（允許短暫超過直到清理執行）。每次寫入時 MUST 以低成本方式統計寫入次數，僅在每 100 次寫入時檢查實際列數，不得每次寫入都掃描整表。實際清理 MUST 由每日 03:00（Asia/Taipei）的 GAS 時間驅動觸發器在獨立於使用者請求的排程中執行，將超過 20,000 列的日誌裁剪至 15,000 列；使用者請求 MUST NOT 參與大量列刪除。觸發器安裝 MUST 保持冪等，重複安裝不得產生重複觸發器。

#### Scenario: 寫入時以抽樣方式檢查容量

- **WHEN** 寫入次數尚未達到抽樣間隔
- **THEN** 不檢查工作表實際列數，直接完成日誌寫入

#### Scenario: 達到容量上限由排程清理

- **WHEN** 日誌列數超過 20,000 列
- **THEN** 由每日 03:00（Asia/Taipei）的獨立排程刪除最舊資料使列數回到 15,000，使用者請求不執行大量刪除

### Requirement: 日誌寫入失敗不得阻斷主流程

寫入日誌的動作 MUST 包覆例外處理；任何日誌寫入失敗 MUST 僅記錄於伺服器錯誤日誌，不得使原本請求回傳失敗，也不得回滾已完成的商業操作。

#### Scenario: 日誌寫入發生例外

- **WHEN** 寫入日誌工作表時擲出例外
- **THEN** 伺服器錯誤日誌留下記錄，原請求仍回傳原本的成功或失敗結果

### Requirement: 僅系統管理員可查閱操作日誌

前端 MUST 提供操作日誌頁籤，且僅對系統管理員顯示。前端導覽與頁籤切換 MUST 依目前使用者角色過濾，防止直接竄改狀態進入管理員頁籤；後端 RBAC MUST 獨立拒絕非管理員請求，不得僅依賴前端隱藏。頁籤 MUST 支援依時間、操作者與事件類別篩選、分頁瀏覽，並可展開單一列查看詳情 JSON。時間篩選採 Asia/Taipei 時區的日期區間（起日 00:00:00 至訖日 23:59:59，含端點），清單依時間戳記遞減排序。為控制讀取整張工作表的成本，`getActivityLog` MUST 預設僅回傳最近 7 天的資料、每頁 50 列、單次最多 500 筆，回傳結構含總筆數、目前頁碼與每頁筆數。

#### Scenario: 管理員查閱日誌

- **WHEN** 系統管理員開啟操作日誌頁籤
- **THEN** 看到預設最近 7 天、依時間遞減排序的分頁日誌清單，並可依時間區間、操作者與事件類別篩選及展開詳情

#### Scenario: 非管理員無法查閱日誌

- **WHEN** 非系統管理員嘗試讀取操作日誌，或竄改前端狀態進入日誌頁籤
- **THEN** 看不到頁籤內容，且 API 請求被後端拒絕

#### Scenario: 查詢成本控制

- **WHEN** 管理員未指定時間區間即查詢日誌
- **THEN** 僅讀取並回傳最近 7 天、最多 500 筆的資料，而非整張工作表
