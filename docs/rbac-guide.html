依帳號角色管理權限 (RBAC) 實作教學

本教學詳細介紹如何在 GAS-Course-Web-Template 專案中新增角色、定義權限矩陣，並於前後端實施完整的權限防護。

1 權限體系核心概念與架構

本專案採用 RBAC（Role-Based Access Control，基於角色的存取控制） 架構，使用者與權限不直接綁定，而是透過「角色」作為中介：

1. 身分驗證 Google GIS / Workspace 登入取得 Email
2. 角色查表 試算表「系統設定與授權」白名單
3. 快取 Session CacheService 儲存 Token、角色與權限
4. 權限守衛 後端檢查 Action · 前端控制介面

預設內建的三種基礎角色：

角色代碼 中文顯示名稱 存取層級 預設權限範圍
admin 系統管理員 全域最高權限 ["*"]（可執行所有 API、修改系統參數與管理成員）
staff 業務人員 業務讀寫權限 ["getSession", "logout", "getCourseIndex", "getCourseIndexStats", "getSystemSettings", "importCourseCodes"]
viewer 檢視人員 唯讀查詢權限 ["getSession", "logout", "getCourseIndex", "getCourseIndexStats", "getSystemSettings"]（僅能檢索與讀取設定，無法匯入或修改）

2 步驟一：在後端定義角色與中文名稱

中文角色名稱集中於 gasRuntime.js 的 ROLE_DEFINITIONS，供後端各模組共用；databaseInitializer.js 的 normalizeRole() 會參照該定義，同時接受中文名稱與英文代碼。若要新增角色（例如 manager 主管），請在 gasRuntime.js 加入定義，並於 normalizeRole() 增加比對：

gasRuntime.js（角色名稱單一來源） 
const ROLE_DEFINITIONS = {
  admin: "系統管理員",
  manager: "主管人員",   // 👈 1. 新增角色代碼與中文標籤
  staff: "業務人員",
  viewer: "檢視人員"
};
databaseInitializer.js（標準化比對） 
function normalizeRole(role) {
  const r = String(role || "").trim().toLowerCase();
  if (r === ROLE_DEFINITIONS.admin || r === "admin") return "admin";
  if (r === ROLE_DEFINITIONS.manager || r === "manager") return "manager"; // 👈 2. 支援中文與英文比對
  if (r === ROLE_DEFINITIONS.staff || r === "staff") return "staff";
  if (r === ROLE_DEFINITIONS.viewer || r === "viewer") return "viewer";
  return r || "viewer";
}
💡 設計亮點：normalizeRole() 同時支援輸入中文與代碼，讓試算表管理員即便在儲存格輸入「主管人員」或「manager」，後端都能正確辨別。

3 步驟二：設定後端權限矩陣 (ROLE_PERMISSIONS)

所有 action 與角色允許清單集中於 actionRegistry.js 的 ACTIONS 登錄表；webApi.js 的 ROLE_PERMISSIONS、公開／寫入／鎖定 action 清單皆由該表產生，不再手動維護多份陣列。新增 action 時必須同時完成登錄、路由與前端 mock handler，否則一致性測試會失敗。

actionRegistry.js（action 登錄表） 
const ACTIONS = {
  ping: { public: true },
  getPublicConfig: { public: true },
  login: { public: true },
  loginWithActiveUser: { public: true },
  getSession: { roles: ALL_ROLES },
  logout: { write: true, roles: ALL_ROLES },
  importCourseCodes: { write: true, locked: true, roles: ["admin", "staff"] },
  getCourseIndex: { roles: ALL_ROLES },
  getCourseIndexStats: { roles: ALL_ROLES },
  getSystemSettings: { roles: ALL_ROLES },
  saveSystemSettings: { write: true, locked: true, roles: ["admin"] },
  getAccounts: { roles: ["admin"] },
  saveWhitelist: { write: true, locked: true, roles: ["admin"] }
};

// webApi.js：由同一份登錄表產生，不需重複列舉
const ROLE_PERMISSIONS = ACTION_REGISTRY.buildRolePermissions();
🔒 後端防護機制：所有請求抵達 routeWebApiAction() 前，均會經由 authorizeWebApiAction() 進行驗證。角色權限採明確 action 列舉，不再以 getXxx 通配規則自動授權；未登錄的 action 會直接回傳 unknown_action，角色不符則回傳 { ok: false, error: "forbidden" }。

4 步驟三：前端設定同步與權限守衛

為了提供良好的使用者體驗，前端介面應配合權限進行相應的隱藏或禁用：

3.1 前端角色對照字典

在 webapp/js/config.js 同步更新角色字典，供導覽列或使用者頭像顯示中文：

webapp/js/config.js 
roleNames: {
  admin: "系統管理員",
  manager: "主管人員", // 👈 新增
  staff: "業務人員",
  viewer: "檢視人員"
}

3.2 按鈕與操作權限守衛

在特定功能頁面中（例如匯入按鈕），透過 MEA.state.user.perms 判斷是否具備權限：

webapp/js/imports.js 或自訂模組 
const user = MEA.state.user || {};

// 檢查是否具有特定 Action 權限或具備最高權限 *
const canImport = user.perms && (user.perms.indexOf("*") !== -1 || user.perms.indexOf("importCourseCodes") !== -1);

// 控制按鈕狀態
if (!canImport) {
  submitBtn.disabled = true;
  submitBtn.title = "您目前的角色無權限執行匯入";
}

3.3 導覽頁籤（Tab）過濾

若希望「系統設定」或特定頁籤僅供指定角色看到，可在 webapp/js/ui.js 的 renderNavbar() 過濾頁籤：

webapp/js/ui.js (renderNavbar 函式) 
function renderNavbar() {
  const user = MEA.state.user || {};
  const tabs = (MEA.config.tabs || []).filter(function(tab) {
    // 範例：設定頁籤僅 admin 可見
    if (tab.id === "settings" && user.role !== "admin") return false;
    // 範例：主管報表頁籤僅 manager 或 admin 可見
    if (tab.id === "managerReport" && user.role !== "admin" && user.role !== "manager") return false;
    return true;
  });
  // ... 渲染頁籤 HTML
}

5 步驟四：指派使用者角色

💡 首次管理員開通：初始化後白名單為空時，登入鏈會在明確允許開通的條件下，讓第一位成功驗證的 Google 帳號成為系統管理員；寫入於短鎖臨界區完成並再次確認白名單仍為空，避免並發搶占。後續角色調整請由管理員在此頁籤或試算表為之。

您可以透過兩種途徑指派與調整使用者的角色：

  1. 透過 Web App 設定頁籤操作（推薦）：
    以 admin 登入 Web App，進入「系統設定與授權」頁籤，在白名單成員區塊點擊「＋ 新增授權成員」，輸入使用者的 Google Email 並從下拉選單指派角色。
  2. 直接編輯 Google 試算表：
    開啟試算表的「系統設定與授權」工作表，在右側區塊 D1:G（Email、姓名/職稱、角色、啟用狀態）直接輸入即可。

6 完整實戰：新增「稽核主管 (auditor)」角色

假設需求：新增一個名為「稽核主管（auditor）」的角色，該角色能檢視課程清單與系統參數，但不能執行任何修改或匯入動作。

1. 修改 gasRuntime.js 的 ROLE_DEFINITIONS： 

const ROLE_DEFINITIONS = {
  admin: "系統管理員",
  auditor: "稽核主管",   // 👈
  staff: "業務人員",
  viewer: "檢視人員"
};

2. 修改 databaseInitializer.js 的 normalizeRole()，並在 actionRegistry.js 的 ALL_ROLES 與各 action 的 roles 加入 auditor： 

const ALL_ROLES = ["admin", "auditor", "staff", "viewer"];

const ACTIONS = {
  getCourseIndex: { roles: ALL_ROLES },       // 👈 稽核主管可查課程
  getCourseIndexStats: { roles: ALL_ROLES },
  getSystemSettings: { roles: ALL_ROLES },    // 👈 稽核主管可讀設定
  getSession: { roles: ALL_ROLES },
  logout: { write: true, roles: ALL_ROLES },
  importCourseCodes: { write: true, locked: true, roles: ["admin", "staff"] }, // 稽核主管不可匯入
  saveSystemSettings: { write: true, locked: true, roles: ["admin"] },
  getAccounts: { roles: ["admin"] },
  saveWhitelist: { write: true, locked: true, roles: ["admin"] }
};

3. 修改 webapp/js/config.js： 

roleNames: {
  admin: "系統管理員",
  auditor: "稽核主管",   // 👈
  staff: "業務人員",
  viewer: "檢視人員"
}

4. 修改 webapp/js/accounts.js（在彈跳選單加入該選項）： 

<select id="newAccountRole" class="select">
  <option value="viewer">檢視人員 (viewer)</option>
  <option value="staff">業務人員 (staff)</option>
  <option value="auditor">稽核主管 (auditor)</option>
  <option value="admin">系統管理員 (admin)</option>
</select>

7 單元測試與上線驗證

修改完成後，建議依序執行以下驗證流程：

  1. 執行 Node.js 單元測試： 
    npm test
    確認既有的權限機制與代碼正規化皆全數通過。
  2. 重新建置前端單一 HTML： 
    npm run build:webapp
    打包腳本會自動將更新後的 webapp/ 檔案重新內嵌至根目錄的 index.html。
  3. 推送部署至 Google Apps Script： 
    npm run push
    立即生效於線上試算表與 Web App 網頁！
