GAS Web App 全端架構與通訊協定完全指南

深入剖析 Google Apps Script 網頁版之核心工程限制：單一 HTML 限制破解、避開 CORS OPTIONS 預檢之通訊協議、併發寫入鎖定與高效試算表存取準則。

1 單一 HTML 限制與零依賴打包原理

Google Apps Script 的 HtmlService 在執行 createTemplateFromFile('index').evaluate() 輸出網頁時，有著一項嚴格的硬體限制：不支援外部相對路徑的 <link rel="stylesheet" href="..."> 或 <script src="...">。

如果把 CSS 與 JS 全寫在同一個 index.html 中，程式碼將超過數千行，極度難以維護。本專案採用「開發時模組化，發布時內嵌化」的架構：

開發階段 webapp/ 下 12 個 JS 模組與 styles.css，另與根目錄共用模組協作
建置腳本 scripts/build-webapp.js
產出目標 根目錄單一 index.html
雲端執行 HtmlService 快速渲染
💡 為什麼不用 Webpack / Vite？
Webpack 或 Vite 需要龐大的 node_modules（動輒數百 MB）與複雜的轉譯設定。本專案的 scripts/build-webapp.js 是純原生 Node.js 腳本，透過簡單正規表達式將檔案內容逐一插入 <style> 與 <script> 區塊，建置耗時不到 50 毫秒，零相依、零設定負擔！
🧩 單一來源模組：gasRuntime.js 統一 GAS／Node 相依解析、白名單全域注入與工作表／角色／版本號常數；courseNormalizationShared.js 由前後端共同引用，避免正規化規則漂移；actionRegistry.js 統一 action 登錄、公開／寫入／鎖定清單與 RBAC 矩陣。建置產物另注入 MEA_PRODUCTION_BUILD 標記以停用正式環境的 Mock 模式，CI 會檢查建置產物是否與原始碼一致。

2 繞過 CORS OPTIONS 預檢請求的關鍵技術

當現代瀏覽器以 JavaScript fetch() 發送 POST 請求時，若標頭指定為 Content-Type: application/json，瀏覽器會強制發送一次 HTTP OPTIONS 預檢請求 (Preflight Request)。

⚠️ GAS 的致命陷阱：Google Apps Script 的 Web App 完全不支援 HTTP OPTIONS 方法！若瀏覽器發出 OPTIONS 預檢，Google 伺服器會直接回應 HTTP 405 Method Not Allowed，導致前端 API 呼叫永遠失敗。

本範本的解決方案（通訊協議黃金標準）：

前端發送請求時，強制將 Content-Type 設為 text/plain;charset=utf-8，內容傳送 JSON 字串：

webapp/js/api.js (前端發送) 
// 將 Content-Type 設為 text/plain，瀏覽器將其視為「簡單請求 (Simple Request)」
// 依 W3C CORS 規範，簡單請求完全不會觸發 OPTIONS 預檢！
fetch(apiUrl, {
  method: "POST",
  headers: {
    "Content-Type": "text/plain;charset=utf-8"
  },
  body: JSON.stringify(body)
})

後端 webApi.js 則透過 e.postData.contents 解析字串為 JSON 物件：

webApi.js (後端接收) 
function parseWebApiPayload(e) {
  if (e && e.postData && typeof e.postData.contents === "string") {
    try {
      return JSON.parse(e.postData.contents);
    } catch (err) {
      return null;
    }
  }
  return e && e.parameter ? e.parameter : {};
}

3 統一信封通訊協議 (Envelope Pattern)

為了確保所有模組與端點的通訊具有高度一致性與可預測性，系統統一套用信封結構：

請求信封格式 (Request Payload)

{
  "action": "importCourseCodes", // 👈 必填：欲執行的 API 操作名稱
  "token": "gas_xxx_xxxxxx",     // 👈 鑑權：由 login 取得的 6 小時 Session Token
  "rows": [ ... ],               // 👈 業務資料載荷
  "preNormalized": true
}

回應信封格式 (Response Payload)

// 成功時
{
  "ok": true,
  "rows": 1250,
  "stats": { ... }
}

// 失敗時
{
  "ok": false,
  "error": "forbidden",           // 機器可讀之標準錯誤代碼
  "message": "目前角色無權限執行此操作" // 人類可讀之繁體中文提示訊息
}

4 併發寫入防護：LockService 排隊機制

Google 試算表本質上不具備關聯式資料庫的行級鎖（Row Lock）。當多個使用者同時按下「儲存設定」或「匯入課程」時，若同時執行 setValues() 會發生後者覆蓋前者（Race Condition）甚至資料錯亂。

本範本的解法：在 webApi.js 的 doPost 中，所有標記為寫入型的 Action（如 importCourseCodes、saveSystemSettings）會自動請求 ScriptLock：

webApi.js (doPost 鎖定邏輯) 
let lock = null;
let hasLock = false;

try {
  // 檢查是否為需要鎖定保護的 Action
  if (needsLock && typeof LockService !== "undefined") {
    lock = LockService.getScriptLock();
    // 最多等待 15 秒排隊，避免並發卡死
    hasLock = lock.tryLock(15000);
    if (!hasLock) {
      return jsonResponse(webApiError("lock_timeout", "系統繁忙中，請稍候片刻再試"));
    }
  }

  // 安全執行業務邏輯寫入
  const result = routeWebApiAction(action, payload, e);
  return jsonResponse(result);
} finally {
  // 保證必定釋放鎖定
  if (hasLock && lock) {
    lock.releaseLock();
  }
}

5 效能快取：CacheService Session 管理

試算表讀寫非常耗時（每次 getValues() 需耗費 200~800 毫秒）。如果使用者的每個操作都要去試算表驗證身分與權限，系統會極度遲鈍。

解決方案：利用 Google 的記憶體級分散式快取 CacheService.getScriptCache() 儲存 Session：

  • 使用者登入成功後，簽發 gas_隨機碼 Token。
  • 將使用者的 Email、姓名、角色與權限清單存入快取，有效期限設為 6 小時 (21,600 秒)。
  • 後續請求讀取快取僅需 小於 5 毫秒，兼顧安全性與極致反應速度。

6 試算表作為資料庫 (Spreadsheet as DB) 效能最佳實踐

當使用 Google 試算表作為 Web App 的後端持久層時，請遵循以下由 Exam-Sections-Arranger 淬煉出的架構原則：

最佳實踐原則 為什麼重要？ 如何落實？
純資料工作表
(No Formula) 		若工作表內包含 VLOOKUP、SUMIF 或陣列公式，大批量寫入時會觸發全表公式重算，造成 GAS 執行逾時（超過 6 分鐘限制）。 後端工作表（如「正規化課程代碼」）一律存放純純文字與數值，所有業務運算與轉譯由後端 JS 完成後再以純文字寫入。
批次分塊寫入
(Chunking) 		一次 setValues() 寫入超過 10,000 筆紀錄時，容易引發記憶體溢出或 Google 內部 RPC 失敗。 在 subjectCodeTransformer.js 中將大陣列以 COURSE_INDEX_WRITE_CHUNK_SIZE = 5000 分批迴圈寫入。
純文字格式設定
(@STRING@) 		班級代碼（如 301201）或課程代碼常以數字開頭，若被試算表自動轉為數值會遺失前導零或科學記號化。 在寫入前呼叫 range.setNumberFormat("@")，確保所有代碼欄位完整保留。

7 全端資訊安全防護架構 (Security Hardening)

為防範雲端環境與試算表資料庫常見的攻擊面，本範本實作了五大深層安全防禦：

防護維度 潛在風險與威脅 實作機制與防護邏輯
試算表公式注入防護
(Formula Immunization) 		惡意使用者於姓名、設定或課程欄位輸入 =CMD(...)、+123、@SUM(...) 等，當試算表開啟或匯出 CSV 時可能觸發非預期執行或資料外洩。 在 utilities.js 提供 sanitizeFormulaValue 與 sanitizeRowMatrix，寫入試算表前對 =、+、-、@、\t、\r 開頭字串自動附加前置單引號跳脫。
CSPRNG 密鑰隨機度
(RFC 4122 v4 UUID) 		使用 Math.random() 產生的 Token 隨機度較低，在長時間運行或高併發下可能遭受預測或碰撞攻擊。 在 webApi.js 的 generateSessionToken() 中，支援呼叫 Google Apps Script 原生 Utilities.getUuid()，具備密碼學安全之高品質真隨機強度。
Google ID Token 嚴格校驗 若後端驗證 JWT 時略過 aud 欄位，攻擊者可持任意其他 GCP 專案簽署的合法 Google Token 矇混登入。 強制檢查後台必須預先設定 Client ID；後端驗證時嚴格比對 info.aud === cleanClientId，徹底阻斷跨應用憑證混淆漏洞。
HTTP GET 白名單
(Default Deny) 		允許透過 GET 呼叫敏感 API 會導致 Session Token 被記錄在瀏覽器歷程紀錄、代理伺服器或存取日誌，並易遭受 CSRF 繞過。 doGet 實施預設拒絕政策：除 ping 與 getPublicConfig 供唯讀檢查外，其餘所有 action 強制拒絕 GET 並要求使用 POST。
前端 XSS 編碼防護 動態組合 HTML 行內屬性（如 onclick）時，若變數含有單引號或 HTML 特殊符號可能導致腳本注入攻擊。 所有使用者輸入在前端渲染時全面通過 MEA.ui.escapeHtml()，行內按鈕傳參則採用 decodeURIComponent(encodeURIComponent(...)) 隔離字串。
